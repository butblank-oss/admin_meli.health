## 0. 이 문서를 읽는 법

이 문서는 **두 제품 중 어느 쪽이 더 낫다**를 가리는 문서가 아닙니다.
조사해 보니 **서로 앞선 데가 달랐습니다.** 그래서 한 방향 이식표가 아니라 양방향입니다.

- **2장**은 사실 관계입니다. 추측과 확인을 구분해 적었습니다.
- **5장**이 실제 작업 목록입니다. 개발 논의는 여기서 시작하면 됩니다.
- **6장 `[확인 필요]`** 는 제가 바깥에서는 판단할 수 없던 것입니다. 이 여덟 가지 답에 따라
  1차 범위가 달라집니다. **가장 먼저 답을 주셔야 하는 부분입니다.**

항목 번호는 고정입니다. `B-03`, `M-01` 처럼 불러 주세요.

### 4.3.1 파트너(병원) 쪽 통제 — 사내 가이드로 확인

번들에는 안 보였지만 **사내 가이드에 다 적혀 있었습니다.** 병원 운영자도 마스킹 해제를 합니다.

> 고시가 권고하는 조합·길이에 못 미칠 소지가 있습니다. 2단계 인증이 있어 보완되기는 하나

### 4.3.2 맬리의 민감정보 열람 모델 — 닥터 대시보드

가장 배울 게 많은 대목입니다. 맬리는 건강정보를 **상시 열어 두지 않고, 네 조건이
동시에 맞을 때만 30분 동안** 엽니다.

| 조건 | 내용 |
|---|---|
| 동의 | 환자가 **제3자 정보 제공 동의**를 끝냈을 것 |
| 소속 | 그 **채널(병원)에 매칭**돼 있을 것 |
| 역할 | **닥터 계정**일 것 (운영자 계정으로는 못 봄) |
| 행위 | 환자가 **직접 NFC 패드에 태깅**할 것 |

> *"NFC는 환자가 제3자 정보 제공 동의를 완료하고 해당 채널에 매칭된 상태일 때 제공되며,
> 이때 **닥터 계정만** 해당 환자의 재활·건강 요약 정보를 확인할 수 있습니다."* (앱서비스 가이드 Q&A)

그리고 **시간으로 끝납니다.**

> *"환자 정보 열람은 **태깅 후 30분간** 가능하며, 시간이 지나면 **'열람만료'**로 표시됩니다."*
> *"30분간 태깅한 환자의 건강 관리 기록을 열람할 수 있습니다."* (닥터 가이드 §1-3, §3-3)

열람 이력 화면에 **만료 상태가 그대로 남습니다.** 닥터는 "내 환자 전체"를 보는 게 아니라
**지금 내 앞에 온 그 사람만, 30분만** 봅니다. 화면에 뜨는 이름조차 마스킹돼 있습니다.

> *"사용 종료 후 **반드시 로그아웃**해 주세요. 미로그아웃 상태로 인한 개인정보 유출 발생 시

> 시스템이 끊어 준다면 이렇게 쓸 이유가 없습니다. **사람에게 책임을 넘기고 있습니다.**
> 하필 닥터 대시보드는 **진료실 공용 화면**이라 유휴 차단이 가장 필요한 자리입니다.
> 고시 제6조 대상이고, `M-02` 는 1차로 확정입니다.
>
> **`C-03` 은 해결됐습니다 — 있습니다.** 2차 DB 에 `로그인 비밀번호 5회 연속 오류 시 30분 계정 잠금 및 자동 해제`
> (배포완료 09-21)가 있습니다. 맬리브레인 P-8 은 5회 잠금만 정해 뒀고 **해제 방식이 비어 있으니**,
> 맬리 규격(30분 자동 해제)에 맞추면 됩니다 → `B-13`.
>
> **가이드의 "비밀번호 4자리"는 최초 발급 임시 비밀번호로 보입니다.** 같은 가이드에
> "최초 로그인 후 비밀번호 변경" 안내가 있고, 2차 DB 에 `비밀번호 재설정 시 유효성 기준 안내가 없으며…`
> (배포완료 09-21)가 있어 **검증 자체는 돌고 있습니다.** 기준값만 받으면 `M-09` 는 닫힙니다.
>
> **`C-08` 은 해결됐습니다.** 사내 가이드에 답이 있었습니다 — 파트너(병원)도 마스킹 해제를 하고,
> 민감정보는 **의료진/특수 권한 계정만** 따로 볼 수 있습니다 (4.3.1). 번들에 안 보인 것은
> 캡처된 청크에 해당 라우트가 없었기 때문입니다.

## 7. 합칠 때 — 권한·로그를 같은 체계로

"합친다 — 권한·로그를 같은 체계로" 로 정해졌으므로, 지금 결정해 둘 것.

### 7.1 권한 코드

맬리는 `/adm` ↔ `/mng` 쌍으로 이미 갈라 두었습니다 —
`MELI_MEMBERS` ↔ `MELI_MANAGER_MEMBERS`, `MELI_NFC` ↔ `MELI_MANAGER_NFC` 등.

맬리브레인도 **같은 규칙**을 따릅니다. 새 접두사를 만들지 말고 기존 책에 맞춥니다.

```
MELI_CARE_PARTICIPANTS   ↔  MELI_MANAGER_CARE_PARTICIPANTS
MELI_CARE_APPLICATIONS   ↔  MELI_MANAGER_CARE_APPLICATIONS
MELI_CARE_CONSULT        ↔  MELI_MANAGER_CARE_CONSULT
MELI_CARE_REPORT         ↔  MELI_MANAGER_CARE_REPORT
MELI_CARE_AUDIT          ↔  MELI_MANAGER_CARE_AUDIT
```

역할도 맬리 7종(`system` `masterAdmin` `serviceAdmin` `contentsAdmin` `manager`
`doctor` `classManager`)에 맞춥니다. 케어센터 주무관 = `manager`,
주/부 구분은 역할이 아니라 **(사람 × 그룹) 좌석 속성**으로 둡니다.

### 7.2 열람 로그

한 테이블로 합치려면 **사유 코드가 같아야** 합니다.

- 공통 8종은 맬리 것을 그대로 (`정책-정의서.md` §2.2)
- 케어센터 4종(미활동자 안부 연락 / 위험군 상담 연계 / 참여 신청 확인 / 보건소 공문 회신)은
  **같은 테이블에 제품 구분자와 함께** 둡니다. 별도 테이블을 만들지 않습니다.
- 보관 기간은 **2년**으로 통일합니다. 둘 다 민감정보입니다.

### 7.3 회원·채널 DB — 지금 나뉘어 있어도 나중에 붙을 수 있게

회원 DB 와 채널 DB 는 지금 겹치지 않습니다. 나중에 합칠 때 깨지지 않으려면
**지금 정해 둬야 하는 것**만 추립니다. 대부분 맬리 응답에 이미 답이 있었습니다.

#### 제품 구분자를 새로 만들지 않습니다

맬리 회원 응답에 **`siteId` 가 이미 있습니다** — `"siteId": "meliService"`.
맬리브레인은 여기에 자기 값(`brainService` 등)을 쓰면 **같은 테이블에 그냥 들어갑니다.**
`product` 같은 컬럼을 새로 만들면 나중에 둘을 맞추는 일이 또 생깁니다.

#### 회원 키는 UUID, PIN 은 표시용

| | 맬리 | 맬리브레인 | 합칠 때 |
|---|---|---|---|
| 내부 키 | `id` · `wrsUserUuid` (UUID) | PIN 4자리 | **UUID 로 통일.** PIN 을 키로 쓰면 822명 안에서도 충돌하고, 합치면 확정적으로 깨집니다 |
| 사람을 알아보는 값 | `phone` + `countryCode` (분리 보관) | `+8210…` 한 덩어리 | **맬리 형식으로.** 저장 형식이 다르면 같은 사람을 못 알아봅니다 |

> **한 사람이 양쪽에 다 있을 수 있습니다.** 무릎 수술 후 재활을 받는 분이 치매예방교실에도
> 나올 수 있습니다. 합칠 때 그 두 줄이 한 사람으로 묶이려면 **전화번호 정규화 형식이
> 지금부터 같아야** 합니다. 나중에 맞추면 이미 쌓인 데이터를 전부 훑어야 합니다.

#### 채널은 이미 트리입니다

맬리 `managerGroup` 에 **`parentId` 가 있습니다** (`{"value": "root"}`). 즉 채널이 평평하지 않고
트리로 설계돼 있습니다. 맬리브레인의 계층(지자체 → 기관 → 그룹)을 **이 트리에 그대로 얹으면 됩니다.**

```
root
 ├ 대찬병원                     (맬리 · groupType=company)
 └ 인천 남동구                  (맬리브레인 · 지자체)
    ├ 남동구보건소
    ├ 만수노인문화센터
    └ 남동구노인복지관
```

**기수(3기·4기)는 채널 트리에 넣지 않습니다.** 기관은 그대로인데 기수만 바뀌기 때문입니다.
기수는 채널에 매달린 **프로그램 회차**로 따로 둡니다. 지금 맬리브레인이 `challenge` 로
그렇게 쓰고 있고, 맞습니다.

#### 소속은 상태가 아니라 이력입니다

맬리에 이미 `채널 초대 이력`, `소속 채널 해제`, **`채널별 동의일시를 별도 관리`**
(2차 배포 8/26)가 있습니다. 맬리브레인도 같은 모양이어야 합니다 — 4기 이월 때문에
어차피 필요하고, 합칠 때 "언제부터 어느 채널 소속이었나"가 없으면 과거 열람 기록의
정당성을 따질 수 없습니다.

#### 동의는 (사람 × 채널)마다

같은 분이 병원 채널과 보건소 채널에 다 있으면 **동의도 채널마다 따로**여야 합니다.
맬리가 이미 그렇게 바꿨습니다. 맬리브레인이 동의를 사람 단위로만 들고 있으면,
합치는 순간 "병원에 준 동의로 보건소가 열람"하는 모양이 됩니다.

#### 정리 — 지금 지켜야 할 다섯

1. 제품 구분은 **`siteId`** 로. 새 컬럼 금지
2. 회원 키는 **UUID**. PIN 은 화면 표시용
3. 전화번호는 **맬리 형식**(`countryCode` 분리)으로 저장
4. 채널은 **`parentId` 트리**에 얹고, 기수는 트리 밖 회차로
5. 소속·동의는 **(사람 × 채널 × 시점)** 으로

> 다섯 모두 **스키마 결정**이라 나중에 바꾸면 마이그레이션이 붙습니다.
> 1차에 코드를 안 쓰더라도 **컬럼은 지금 잡아 두는 편이 쌉니다.**

### 7.4 API 경로

맬리 규칙을 그대로 씁니다 — 슈퍼 `/adm/*`, 채널 `/mng/*`.
같은 응답 스키마를 쓰고 **서버가 토큰 보고 범위를 자릅니다.** 화면은 한 벌로 끝납니다.
