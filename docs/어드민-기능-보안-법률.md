## 1. 구조 — 어드민이 왜 두 개인가

| | 채널 어드민 `/` | 슈퍼어드민 `/super/` |
|---|---|---|
| 쓰는 사람 | 치매안심센터 채널관리자 (예: 김주무) | 원메딕스 운영팀 (예: 이운영) |
| 보는 범위 | **자기 채널만** (남동구 822명) | **전 채널** (4개 채널 2,328명) |
| 강조색 | 초록 · 밝은 크롬 | 보라 · **다크 크롬** |
| 권한 축 | Operate — 주어진 범위 안에서 판단·기록 | Own — 원본을 만들고 전 채널에 내려줌 |

겉모습을 다르게 한 것은 안전장치입니다 — 두 어드민을 헷갈리면 전 채널 오발송이 납니다.
권한 모델은 맬리 본서비스(admin.stg ↔ partner.stg)의 소유/운영/조회 3축을 따르고,
**원본(콘텐츠·그룹·계정·판정 기준)은 슈퍼에만** 둡니다. 채널에는 자기 몫만 잘라 내려갑니다.

## 4. 적용되어 있는 보안

### 4.1 개인정보 열람 모델 — 두 어드민 공통

열람은 **문지기를 전부 통과해야** 열립니다. 채널·슈퍼가 같은 모델을 씁니다.

```
[가린 목록] ──이름/행 클릭──> {① 동의 확인} ──> {② 좌석 권한 확인} ──> {③ 사유 + 업무목적 서약}
                                  │철회/미동의          │sens 없음              │미입력
                                  └──차단 모달          └──차단 모달            └──진행 불가
                              ──통과──> [상세 = 원문 열람 · 기록 1건 적재]
                              ──목록으로 나감──> [재마스킹 · 열람 종료 시각(열람 시간) 기록]
```

| 장치 | 내용 | 근거 |
|---|---|---|
| 기본 마스킹 | 이름 `김*순` · 전화 `010-****-1234`가 기본. 원문은 문지기를 거쳐야만 | 법 제23조 제2항 (P-3) |
| 동의 게이트 | 민감정보 **별도 동의** 없거나 **철회**한 분은 열람 자체가 차단 | 법 제23조 제1항 (B-04·05) |
| 좌석 권한 | 건강정보 열람은 역할과 별개로 **좌석마다** 부여 — 주관리자라도 자동으로 안 열림. 채널은 '우리 채널 운영자', 슈퍼는 '계정·권한'에서 관리 | 법 제23조 (B-10) |
| 사유 강제 | 공통 8종(+채널은 케어센터 4종), 기타는 5자 이상, 업무목적 외 조회 금지 서약 체크 필수 | 고시 제8조 (P-4) |
| 열람 = 동선 | 상세 진입이 열람 1건. 나가면 재마스킹되고 **언제까지 봤는지**가 남음. '지금 가리기'로 먼저 닫을 수 있고, 가린 뒤에도 '다시 열람하기'를 남김 | 고시 제8조 (P-5·B-15) |
| 열람 범위 | 한 번 열람에 **최근 6개월**까지만. 전 기간이 열리지 않음 | B-11 |
| 운영팀도 같은 문지기 | 슈퍼어드민 열람도 좌석 권한 + 사유를 지나며, 채널 담당자와 **같은 장부**에 쌓여 같은 탐지 규칙에 걸림 | 규칙 S-1 개정 |

- 기본값은 **가린 상태**. 원문 포함을 고르면 사유 필수 안내로 전환 (P-7)
- 내려받기도 열람 기록에 적재되고 월간 점검 대상
- 실서비스에서는 파일 암호 잠금 필요 → B-06 (고시 제7조, 맬리 구현 재사용)

## 5. 법률 근거 × 보완 필요 사항

### 5.1 전제 — 누가 처리자이고 누가 수탁자인가

**보건소(지자체)가 개인정보처리자, 원메딕스가 수탁자**입니다.
보건소에 관리·감독 의무가 생기고, 우리는 보건소가 점검할 수 있는 **증빙을 내줄 의무**가 있습니다.
"수탁자라서 덜 해도 된다"는 성립하지 않습니다. 열람 기록·월간 점검·운영자 로그 화면이
전부 이 증빙 요구에 대응합니다.

### 5.2 조항별 현황 — 프로토타입에 설계됨 vs 실서비스에서 마저 해야 함

프로토타입의 "구현"은 전부 **화면 동작**입니다. 아래 표의 보완 열은
같은 규칙을 **서버에서 강제**하기 위한 작업입니다 (대조표 1차 작업 목록과 번호 연동).

| 법령 요구 | 근거 | 프로토타입 | 실서비스 보완 (필수) |
|---|---|---|---|
| 민감정보는 **별도 동의**로만 처리 | 법 제23조 제1항 | 동의 게이트 설계됨 — 미동의·철회자 열람 차단, 동의 현황 카드 | `agreedSensitive` 등 동의 필드를 서버 스키마에 (B-04), 비동의 회원 마스킹 해제를 **서버가** 차단 (B-05) |
| 민감정보 **안전성 확보조치** | 법 제23조 제2항 | 화면 마스킹, 열람 최소화 동선 | **마스킹을 서버 응답에서** — 원문을 응답에 담지 않기 (B-02), 서버 페이지네이션·필터로 전원 PII 전송 차단 (B-03), 전송·저장 암호화 |

### 5.3 지금 당장 순서 — ① 안 하면 위법 ② 사고 나면 피해 큰 순

1. **채널 간 조회 차단 검증 (C-07)** — 서버가 `workspaceId` 소유권을 검증하지 않으면
   한 센터 담당자가 다른 센터 참여자를 조회할 수 있습니다. 화면 이전에 서버부터.
2. **토큰 노출 제거 (B-01)** — 참여자 목록 응답에 앱 로그인 토큰 필드가 설계돼 있던 문제.
   값이 채워지는 순간 계정 탈취 경로가 됩니다.
3. **서버 마스킹·동의 연동 (B-02~05)** — 화면 마스킹은 응답에 원문이 오면 무의미합니다.
4. **접속기록 서버 적재 + 월 점검 운영 (P-6·16, B-15)** — 지금은 새로고침하면 사라지는
   메모리 기록입니다. 적재가 없으면 고시 제8조 위반이고 보건소 점검 증빙이 없습니다.
5. **인증 체계 (B-12·13, P-17)** — 2단계·잠금·유휴 차단을 서버로.
6. **다운로드 암호 (B-06)**, **위탁계약서 점검 (C-05)**, **파기 규정 (OP-10)**.

## 6. 한 장 요약

- **기능** — 채널은 "한 명이 822명을 운영"하는 14화면(오늘·참여자·현황·상담·일정·챌린지·푸시·리포트·신청·열람기록·운영자·설정), 슈퍼는 "원본을 만들고 전 채널에 내려주는" 16화면(현황·참여자 찾기·채널·기수·계정·로그·편성·콘텐츠·챌린지·CS·발송·이상탐지).
- **보안** — 두 어드민이 **같은 열람 모델**(동의·좌석 권한·사유 → 상세 진입 = 열람 → 나가면 가림 → 전부 같은 장부에 기록 → 이상 탐지)을 쓰고, 되돌릴 수 없는 일에는 확인을 2~3겹 쌓았습니다. 접속기록 5항목·2년·월 점검, 세션 30분 차단, 2단계 인증, WCAG AA 0건까지 화면에 설계돼 있습니다.
- **법률 보완** — 지금 것은 전부 화면입니다. 실서비스 전에 ① 채널 간 조회 차단과 토큰 제거, ② 마스킹·동의·열람 기록의 **서버 강제**, ③ 인증 체계, ④ 다운로드 암호·위탁계약서·파기 규정 순으로 옮겨야 법 제23조·제26조·제21조와 안전성 확보조치 고시(제5~8조)를 충족합니다. 정책으로는 **OP-1(승인↔가입)**이 가장 급합니다.
